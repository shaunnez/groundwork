# Large-pack analysis (integrated collector branch)

This branch combines the bounded report path with the selected-notice hosted GETS collector. The collector integration was deployed only to the isolated `gets-collector-staging` Railway environment; the compact and concurrent analysis changes described below are being qualified locally before another staging deployment. It preserves existing immutable originals, source versions and older reports. Small assessments keep their existing path. A report with more than 100,000 saved characters, 500 saved units, or an admitted pack with partial reader coverage uses `groundwork-segmented-v1`; the high-level analysis contract is `segmented-evidence-v3` and the worker cache version is `worker-v5`.

## Processing and coverage

The API freezes source IDs and hashes at run admission and streams saved units through a preflight. The worker reads up to 100 units per database page. It partitions the exact saved text into segments at line or whitespace boundaries without dropping characters. PDF pages, DOCX paragraphs and tables, and XLSX sheets inherit their reader location; spreadsheet segments add a locatable cell range where cell markers exist. A segment is at most 12,000 UTF-8 bytes, or 2,000 for a sheet, and a batch prompt at most 24,000 bytes. The worker also checks each complete model input, including schema and system prompt, against a conservative 64,000-token upper bound inferred from UTF-8 bytes. Claude output remains capped at 12,000 tokens. A segment that cannot fit fails explicitly. This bounds transport size; it is not a model context guarantee.

New runs ask for a list of every reviewed batch-local segment number and a sparse list of substantive findings. The worker expands that response into one durable outcome per segment, including empty outcomes. Older runs keep their original response contract for safe resume. Paragraphs containing marked proposed or deleted DOCX wording are excluded from high-level model input and recorded as `excluded` in the durable `analysis_segments` ledger with their saved unit and reason. The validator reconciles input IDs with output IDs and checks schema and quote text against the saved segment. Other ledger rows record pending, processed or failed state. Structured findings and requirement occurrences are stored in `analysis_items` with source, unit, segment, location and exact quote. The API pages the full ledger at `/api/runs/:id/analysis-items`. Report requirements show up to 100 distinct examples and explicitly link to the full ledger; duplicates at different source locations remain inspectable. A processed segment proves an outcome was recorded, not that the model found every semantically relevant statement.

The report synthesis selects up to 12 findings per source and 180 overall, then trims the selected list to a 40,000-byte synthesis prompt. Omitted findings stay in the ledger and their count is visible. Synthesis and support review can cite only selected, saved units; report quotes are validated against the original saved unit, then separately reviewed for support. The source inventory, reader gaps, exclusions and selection limit are retained in the report. This is bounded summarisation rather than an exhaustive representation of every extracted finding in the report narrative.

Run stages and provider receipts remain durable. Up to four independent analysis batches run concurrently by default; `analysisConcurrency` in private config or `GROUNDWORK_ANALYSIS_CONCURRENCY` sets a value from one to four. Repeated processing skips fully processed batches; a recorded model stage can be reused without paying for a completed call again. Inputs include source and segment hashes, extraction method, prompt/schema hashes, model and transport version. Interrupted or uncertain provider calls keep their existing reconciliation gate. Cancellation and lease checks run between batches and before database publication. The configured allowance defaults to 96 model calls and 180 minutes for a segmented run; `analysisMaxModelCalls` in private config or `GROUNDWORK_ANALYSIS_MAX_MODEL_CALLS`, and `analysisRunMinutes` or `GROUNDWORK_ANALYSIS_RUN_MINUTES`, provide bounded operator overrides. Preflight adds six calls for synthesis, verification and possible corrections, then blocks admission above the call allowance. A database transaction reserves each run call against that same allowance, including concurrent workers. Historical successful receipts supply an API-equivalent estimate; it is not an actual subscription bill.
