# Hosted GETS document collection handoff

The owner starts **Check GETS now**. A **single-notice** live check queues one authenticated collection job for the selected notice in the same transaction as its saved notice revision, including when a broad public check already imported that revision. Broad current/future checks import public notices and briefs without queuing attachment collection. Rechecking the same selected revision reuses its existing job. Fixture replay does not contact RealMe. The notice-brief attempt limit does not limit selected collection. There is no schedule and collection does not start a pursuit report.

`gets_pack_jobs` is the durable queue. One row is keyed by account and notice revision. Its states are `discovered`, `access_needed`, `downloading`, `downloaded`, `admitted`, `unchanged`, `failed`, `blocked`, and `cancelled`. Leases permit a worker restart to resume. The owner can cancel an active job or explicitly continue a stopped job after fixing its cause. The GETS status panel shows queue size, current RFx, completed, failed and blocked counts, retry count, and actionable failures. A failed or blocked job is never shown as ready.

The worker shares one in-memory Chromium context across the jobs it drains. It signs in only when GETS asks for supplier access, permits the initial sign-in plus at most three re-logins across that batch, and stops on rejected credentials or an interactive RealMe challenge. Browser state and credentials are not persisted. Collection is serial with a one-second request pace. The runtime needs `GROUNDWORK_REALME_USERNAME` and `GROUNDWORK_REALME_PASSWORD` as Railway service variables.

The GETS file table supplies current file identity, name, declared length, SHA-256, and attachment/addendum kind. A fresh pack references the saved public notice revision. Exact unchanged files reuse prior immutable source versions; new or changed files are streamed to disposable scratch storage, checked against their declaration and type signature, and admitted through `importTenderFile`. An initial all-new pack uses the bounded GETS bulk ZIP; a later pack downloads only new or changed files. Scratch is removed after the job attempt. A removed or withdrawn file is absent from the new current pack; older packs and their source versions remain available for historical citations. Limits are 20 current files, 64 MiB per file, 128 MiB per bulk transfer, and three minutes per transfer. These are collection limits, not report-analysis limits.

## Report-analysis integration contract

`GET /api/gets/collections/:id` returns `packReady`, `pack`, and `gaps`. `packReady` means every declared current original has an admitted source receipt. It does **not** assert complete reader coverage. `pack.id`, `pack.noticeRevisionId`, and each `pack.files[]` entry's `fileId`, `sourceId`, `reader`, `coverage`, `state`, and `problem` identify the frozen evidence and unresolved gaps. The analysis pipeline should use only a `packReady: true` job for an exhaustive pack candidate, and must still enforce its own reader-coverage and report-readiness rules. `GET /api/tender-packs/:id` exposes the same versioned pack inventory. No collector path calls a model or creates a report.

For this pilot, `technicalReviewRequired` on a drawings PDF marks engineering interpretation as outside analytical coverage even when its text reader succeeds. The analysis pipeline must not treat a text-read drawing as reviewed engineering evidence.

The collector and large-pack analysis changes are integrated on `codex/hosted-gets-collector`. The report request freezes the selected source manifest and checks reader coverage separately from `packReady`.

## Hosted verification boundary

The isolated Railway environment is `gets-collector-staging` in the Groundwork project. Its database and volumes differ from production. It uses its own generated public domain, and model and public research toggles are disabled there. Its RealMe variables are configured. A Docker browser launch, local fixture test, or a public GETS check alone does not establish hosted authenticated collection. Keep the branch out of production until report analysis and evidence evaluation finish.

On 23 September 2026, a hosted manual single-notice check for RFx 34995788 produced one authenticated pack with all 13 current originals and 13 distinct source receipts. The 58,516,246-byte drawings PDF and the XLSX pricing schedule were retained. All 13 recorded lengths and SHA-256 values matched the GETS declarations. Nine PDFs read fully; three DOCX files and one XLSX file reported partial reader coverage, preserving their embedded-content and revision-state gaps. `packReady` was true, `pack.complete` was false, and the staging database contained zero reports after collection. A second public check returned one unchanged notice and created no new collection job.

In the deployed staging container, a synthetic intercepted GETS/RealMe flow ran Chromium as UID 1000. Two eligible tenders shared one login; three simulated expiries led to three successful re-logins; a fourth was refused. The later selected-notice trial collected RFx 34920325 (7/7) and RFx 34889995 (3/3) in the same Railway environment after their manual public notice checks. For every file in those packs, source linkage, size and SHA-256 matched the GETS declaration. The collector waited for the GETS subscription form, verified its selected RFx and prefilled account details, and left optional mail/category subscription unchecked. The GETS jobs reached `admitted` and `packReady: true`; the reader reported three partial DOCX files in RFx 34920325 and one partial DOCX plus one unread legacy `.doc` in RFx 34889995. Live reports and full reader coverage remain unverified.
